# 最小侵入与版本迁移

## 先选择边界，再修改调用者

默认目标是所有应用窗口、弹层及其中的内容在两眼一致显示，并保留原有交互。先读 [显示与生命周期](display.md) 的创建路径清单，再决定哪些路径能共用一个适配点、哪些必须单独接入。

“更上游”指调用链中共同且稳定的入口，不是盲目改 Android 全局框架。优先顺序通常是：已有扩展接口 → 应用/依赖的公共消息、窗口或内容安装入口 → 少量确有不同生命周期的专用入口。只有证据表明公共入口覆盖不到时，才修改零散调用点，并记录原因。不要为了统一形式接管其他应用或系统窗口。

衡量改动面时看原有文件/类/方法触点、业务调用是否保留、依赖与构建机制的维护成本，以及新版本能否检测入口变化。一条全局替换脚本改了几十个类，仍然是几十处耦合；零源码差异的字节码切面也仍有切点与构建兼容成本。目标是在完整覆盖和行为正确的前提下减少维护触点，不承诺永久零冲突。

## 有源码：公共入口与独立适配层

- 让业务继续调用原 API；公共库只定义通用接口，设备识别、双眼显示、窗口选择和输入处理放在适配层。避免公共依赖反向引用应用类。
- 以集中注册绑定实现，避免每个 Presenter、页面或按钮单独判断设备。注册时机应早于首次使用；异步内容仍要在实际挂载/替换时接入，覆盖恢复过程。
- 选用公开、稳定的生命周期/内容接口。反射私有字段、同名类覆盖、构建期切面等需要明确收益与兼容验证，不能只为“业务文件零改动”引入隐蔽维护成本。
- 修复分散实现后，撤回已被公共入口替代的 import、调用和专用分支；用上游基线对比确认无关逻辑未改。不要顺手格式化整个文件或更新无关依赖。

### 公共消息入口示例

多个调用者最终进入 `MessageHelpers.showMessage(...)` 时，优先在最终显示入口增加可选 presenter，并接通统一取消入口，而不是批量改调用者：

```text
原业务/依赖调用 → 公共消息 API → 主线程上的通用 presenter
                                  ├─ 已处理：当前双眼窗口显示
                                  └─ 未处理：原消息路径
```

保留资源/格式化/异常重载、长短时长、截断、替换与取消语义。定义未处理/异常的回退行为；回退直接走原内部实现，避免重新调用公共入口形成递归。旧 Toast 的清理计时不得取消新 presenter 消息；窗口失焦/销毁、重新注册与取消应处理所有权，不保留强 Activity 引用。验证普通设备、无前台窗口、后台线程、替换、取消和回调异常。直接调用 `Toast.makeText` 或使用另一套工具类的路径仍须审计。

### 子模块与可复现构建

先查构建实际解析到哪份依赖，特别是根子模块、嵌套副本和相邻目录覆盖。改动依赖时提交到可拉取的 fork/分支，先发布依赖提交，再更新主仓库 URL 与固定提交。验证远端可达、依赖指针一致以及所选构建使用该实现；不要只推主仓库，留下本地 dirty 子模块。新增 fork/推送沿用用户授权范围，不把修改技能视为外部发布许可。

## APK-only：相同原则，换成可验证的补丁

- 先固定用户指定 APK 的包名、版本、哈希、签名、ABI 和 SDK；旧版只作参考/回滚。反编译后追踪公共 helper、窗口工厂、内容安装点和 Surface 路径，优先补丁共同方法并注入少量适配类。
- 用方法签名、调用关系、指令/资源上下文定位；混淆后重找语义入口。补丁验证原始内容、预期匹配数量及修改后结构，匹配缺失或多义时停止该补丁并重新定位，不静默跳过或模糊套用。不要沿用旧版固定行号/偏移作为唯一定位依据。
- 保持原返回值、寄存器/类型、分支、异常范围和生命周期；仅需 DEX 修改时尽量保留无关资源。补丁集中并可重复执行，重复应用应明确识别已修改或拒绝，不能二次注入。
- 更新版本时在新 APK 上重新识别入口并应用补丁，不逐处照搬旧 smali。只有缺少可靠公共入口时才保留分散补丁，并统计触点、列出未覆盖路径。
- 验证重编译、对齐/签名、重新解码及目标方法的实际输出，再做窗口/交互实测。工具执行成功、修改数量更少或首页截图都不证明完整覆盖。

### 混淆入口与覆盖清单重建

相似度比较只用于找候选，不能作为补丁授权条件。可按 Smali 行或指令序列比较，临时忽略 `.line`、`.source` 和混淆类型名；随后必须核对真实的继承链、方法签名、字段类型、寄存器和调用关系，再保存新版原文哈希与精确匹配条件。大类优先按行比较，避免逐字符比较耗时过长。

重新扫描全部原始 DEX 的 `Toast.makeText`、`Dialog.show`、`PopupWindow` 构造、WindowManager add/update/remove、`showSoftInput` 和 insets show 等窗口入口，不只遍历旧版待修改文件。新增 SDK 提示也可能漏掉双目。数量变化时先定位新增/移除调用，再更新预期数量；不能为了让测试通过而直接改计数。Insets 的 `show(I)` 要查看类型掩码，显示状态栏不是请求输入法，不应全部当成 IME 拦截。

### 多 DEX 与方法引用上限

1. 从输入 ZIP 枚举所有 `classes*.dex` 并固定哈希，为 helper 分配未占用的 DEX 编号。上游从两个 DEX 增至三个时，原先的 `classes3.dex` 已属于业务内容；不要继续写到旧 helper 位置。构建、打包允许清单、反汇编验证和测试夹具的编号要一起更新。
2. 主 DEX 接近 65,536 个方法引用上限时，即使 helper 放在独立 DEX，主 DEX 新增的调用引用仍可能超限。Smali 重组时报 `Unsigned short value out of range` 时，先核对 DEX 引用数量及具体指令类型，不直接认定为业务代码错误或一律认定为方法数超限。
3. 确认为方法引用超限后，可迁移少量不改变逻辑的实现类到新增 DEX，释放主 DEX 的引用空间。选择具体类应依据依赖和引用统计，不把某个播放器类固定为所有项目的迁移对象。先核实运行时多 DEX 加载条件；Android 21+ 原生支持，较低版本还需审查启动类和 multidex 初始化。
4. 迁移类保存输入哈希；对最终 APK 与原 APK 使用同一反汇编工具，比较迁移类的声明、字段、注解、指令、分支和异常表。允许明确忽略重组后消失的调试 `.line` 和反汇编器生成的整行注释；不能忽略寄存器、常量、方法签名或操作码来掩盖差异。调试信息不同不等于执行逻辑变化。
5. 验证原业务类集合恰好保留一次，迁移前后的类没有缺失或重复；验证所有受改 DEX 到 helper 的引用能够解析。对未改 DEX 和资源/native ZIP 条目做逐项哈希比对。完成这些静态验证仍不等于运行时已验收。

### 构建版本和验收范围

同一仓库若保留电视专用修复版、诊断包或旧版本构建脚本，各自固定输入版本；更新主适配的配置时，不要让仍使用旧混淆入口的其他构建脚本自动读取新版 APK。

覆盖安装前核实目标设备及已安装签名，保留旧 APK，使用保留数据的更新方式。安装后核对版本、安装文件哈希和数据目录状态。用户要求保持关闭时不启动，报告明确写“已安装，未做本版播放/物理手势验收”。源码文件未变或旧版验收通过，都不足以替代新版本的实际窗口、左右触摸板和视频回归。

本节来自 myDV 2.0.31 的实际迁移：上游增加第三个 DEX、主 DEX 注入后超限、新增一处 SDK Toast，以及迁移类反汇编中的调试行/注释差异。具体类映射、哈希、计数和设备证据保存在项目中，后续版本重新生成。

## 更新上游后的检查

对比新旧创建路径和公共方法语义，特别是新增页面、独立弹窗、消息旁路、内容挂载时机与渲染路径。源码合并无冲突、补丁匹配成功是起点；新版本可能绕过旧公共入口而静默漏适配。

验证代表性公共路径及已登记例外：延迟登录页、对话框按钮/遮罩、Popup/Tooltip、加载/错误/退出提示、视频叠层；检查打开/关闭/替换/恢复和当前窗口焦点。系统窗口或未获设备验证的路径明确列为待验证，不能从清单删除后称“全部完成”。用户暂停设备操作时继续允许范围内的源码/构建工作，报告保留实机边界。
