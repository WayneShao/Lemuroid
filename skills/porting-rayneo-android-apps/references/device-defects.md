# X3 Pro 已观察到的设备与固件缺陷

适用范围：本地 RayNeo X3 Pro（ARGF20 / MercuryLiteXR，Android 12 / API 32）的实际使用记录。作为该设备/固件的兼容性缺陷处理；未经验证不推广到全部雷鸟型号、固件或全部 GPU 路径。刷机或换设备后重新核实。

## 特定硬件加速双眼绘制路径可能触发整机重启

2026-09-16 CloneTTS 0.7.0 适配中，多次点击导入后，应用内文件选择页刚显示、尚未选择文件就整机重启。文件权限授予后仍复现；绕过文件页直接读取 Download 中的 ZIP 并调用原导入逻辑成功。随后仅对文件页设置 Activity `android:hardwareAccelerated="false"`，同时将原生双眼容器调整为参考 Legado 的逐子 View `drawChild` 绘制，用户实机确认文件页正常、故障消失。用户另报告此前高性能双目绘制工作中，启用硬件加速也出现类似整机重启。

工程结论：将“特定硬件加速双眼绘制可能触发整机重启”列为这台设备的已知兼容性缺陷与首要排查项。整机重启与修复后的正常运行已观察到；硬件加速是高度怀疑的触发条件。此次同时修改了绘制实现，没有单变量 A/B，也没有能直接归因 GPU 驱动的内核日志，因此不要写成已证明某个 GPU/驱动函数故障或所有硬件加速均不可用。

处理方式：

- 静态文件页、权限恢复页等轻量普通 View 窗口遇到同类故障，优先局部禁用该 Activity 硬件加速，使用已验证的单内容树双眼绘制；绘制、测量、布局和输入必须使用相同的单眼宽度与启用条件。
- 保留已正常工作的主界面、Compose 和视频/游戏输出。不要把局部规避扩成全应用关闭硬件加速，也不要把普通 View 软件绘制当成 SurfaceView、GL 或视频的通用替代方案。
- 成功规避后保留已验证构建；没有必要仅为拆分根因而再次开启已触发重启的路径。需要进一步研究时按用户明确的研究范围执行。
- 页面刚显示即重启时，优先核对窗口/渲染变化及最后一段日志。尚未选择文件不支持归因 ZIP 内容；shell 可读文件也不证明应用权限。不要为排除无关猜测反复拉取大文件。

## OES 成功会话与动态提示的独立边界

补充证据：Moonlight 12.2 在同类 X3 Pro/2BAU 上使用硬件 HEVC + OES 双眼串流，2026-09-17 会话 boot ID 未变；这不推翻上述特定 HWUI 路径风险，也不证明历史重启根因。该会话还出现“视频双眼正常但动态提示只更新左眼”，扩大 damage/调整软件 layer 均未单独修好，最终独立左右提示控件通过。实现、失败尝试与证据界限见 [OES 双眼视频实战](oes-stereo-field-guide.md)。

## USB ADB 频繁断连

同一设备的 USB ADB 在实际操作中反复断连，包括未发生重启的情况；负载升高时尤其需要考虑传输不稳定。断连本身不证明应用崩溃、设备重启或用户拔线。

- 重连后比较 `/proc/sys/kernel/random/boot_id` 与 `/proc/uptime`，区分单纯传输中断和真正重启；不要把最后一条普通日志直接当成根因。
- **连接尚可用时就先建立 TCP ADB。** 用户已明确要求：发现目标眼镜 ADB TCP 5555 未开启，第一时间执行 `adb -s SERIAL tcpip 5555`，不重复询问，也不等完整探查、传包或断连后才开启。随后连接当前 `IP:5555` 并核对同一设备身份，后续优先使用无线 serial；具体步骤见 [优先建立 TCP ADB](maintenance.md#优先建立-tcp-adb)。默认端口固定为用户指定的 5555，IP 与凭据不固定；这不扩展为自动更改 Wi-Fi 网络或重启设备。
- 需要复现时，将 logcat 连续写到主机本地。采集器可在设备恢复后新建日志分段，并记录主机时间、设备启动标识和 uptime；USB 中断期间的日志可能缺失，主机留存不等于完整内核日志。
- 用户要求停止时结束采集器及其 logcat 子进程，不能让自动重连采集继续运行；不把断连恢复变成自动重启设备或全局重启 ADB 服务。
