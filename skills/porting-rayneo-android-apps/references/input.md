# 输入与返回语义

## 操作模式的约定：默认光标模式

本技能中“光标”专指界面现有的选中框/焦点。用户未指定模式时默认适配光标模式；已明确指定的模式沿用，无需重复询问。用户明确要求鼠标模式时使用小白点模拟鼠标。源码与 APK-only 都遵循此约定；不用两个模式同时消费同一镜腿事件。

| 用户用语 | 滑动行为 | 单击 | 双击 |
|---|---|---|---|
| **光标模式（默认）** | 上下左右滑动，使卡片、按钮、列表项等现有选中框/焦点按方向移动 | 确认当前选中项 | 返回/退出当前层 |
| **鼠标模式** | 滑动增量驱动自由移动的小白点模拟鼠标 | 点击小白点所在位置 | 返回/退出当前层 |

“双击退出”接入应用原有返回语义：有弹窗先关闭当前弹窗，有子页面先返回，根页面才按应用约定退出；保留原有二次退出确认，不直接全局 `finish()` 或杀进程。长按沿用已约定的菜单/上下文动作，不擅自变成模式切换。外接真实鼠标、手柄和系统 DPAD 保留原事件路径。

## X3 Pro 电视应用的双指菜单

电视 App 适配到 X3 Pro 时，默认操作必须包含：上下左右滑动 → 四方向导航，单击 → 确认，双击 → 返回，**双指轻点 → 菜单键 `KeyEvent.KEYCODE_MENU`**。这是双指同时参与的一次操作，与单指双击不同；已有长按菜单也必须补齐双指入口。明确使用鼠标模式时保持其滑动/单击语义，双指菜单仍复用电视 App 的菜单入口。

上述是电视应用的默认映射；用户明确指定的页面级交互优先。例如 Moonlight 首页/设置采用焦点导航和双指 MENU，进入远程串流后双指轻点发送远端鼠标右键，退出采用两组三击确认。不要把电视菜单规则覆盖到已明确约定的远程控制页，也不要把这个串流例外推广成所有电视鼠标模式都使用右键。

- 在已确认的镜腿输入路径识别双指；若 SDK 已交付双指手势枚举，按该层语义接入，不凭空假定一定收到原始多触点事件。原始 `MotionEvent` 路径应跟踪 pointer ID、按下/抬起和移动；不要以 `pointerCount != 1` 一律取消而遗漏双指。
- 双指识别开始时撤销待执行的单击、双击和长按任务，消费整段手势，一次有效双指轻点只派发一次 MENU。两指依次抬起、剩余单指 UP、touch/generic/button release 重复事件，不得再产生确认、返回或方向动作。
- 多指滑动不误判成菜单；取消、三指及以上、窗口失焦/切换、内容失效或 detach 时取消识别，剩余抬起不得激活其他动作。保留真实鼠标、手柄及系统 DPAD 原路径。
- 两指各自记录 pointer ID 和初始位置。第一根手指抬起后，剩余手指的 index 可能改变，仍按 ID 检查后续 MOVE 和最终 UP；任一手指越过阈值都取消菜单候选。在最终 UP 决定是否发送一次 MENU，重复 UP/BUTTON_RELEASE 不再发键。轻点有时长上限，Moonlight 本次使用小于500 ms；此数值是实现选择，不是所有固件的固定手势规格。
- 除 `ACTION_CANCEL` 外，Android 13+ 还应处理 `MotionEvent.FLAG_CANCELED` 标记的 POINTER_UP/UP（例如被系统拒绝的触点）。标记整个多指候选无效，继续消费剩余释放事件；不能让最后一根手指的普通 UP 又触发菜单。
- MENU 分发给当前有效窗口，发送一组 `ACTION_DOWN`/`ACTION_UP`，复用应用原有按键或等价菜单处理；弹层优先处理，禁止穿透触发后台页面菜单。页面不处理 MENU 时，发键成功不等于菜单已显示；先追踪页面原有菜单/上下文菜单入口，不能悄悄改成长按或返回来冒充菜单键适配。
- 验收同时覆盖单指四向/确认/返回、双指菜单一次触发、两指先后抬起、双指移动/取消、弹窗内与播放器内菜单。合成事件或代码中出现 `KEYCODE_MENU` 只证明对应层的实现；真实镜腿双指是否到达、菜单是否出现，必须单独标明物理验收状态。

回归测试至少包含：原单击等待期间进入双指，确认旧点击被取消；两种抬指顺序及剩余单指 MOVE；移动后回原点、第三指、超时、ACTION_CANCEL、FLAG_CANCELED；重复释放；宿主确实只收到一组 MENU 按下/松开。单指导航和页面特定双指右键须独立回归。Moonlight `12.2-rayneo.3` 的 `TwoFingerMenuGesture`、`TwoFingerMenuDispatchTest` 可作源码线索；其主机测试与安装证据不构成实体镜腿菜单验收。

## 光标模式：已有焦点与选中项的导航

优先在公共窗口输入层或既有导航入口实现，复用一套原生内容树、焦点搜索、选中态和列表滚动。不要创建自由移动白点代替选中框，也不要复制第二套可交互控件来制造双眼焦点。

1. **手势转换为方向动作。** 对已确认的镜腿来源识别滑动主轴和阈值，映射到 UP/DOWN/LEFT/RIGHT，优先复用应用已有 DPAD 或等价导航分发。一次普通完成滑动默认触发一个方向动作；需要连续重复时单独定义重复节奏。滑动、长按和取消不能再被识别为单击，touch/hover/generic/button release 的重叠路径要去重。
2. **以当前窗口为作用域。** Activity、Dialog、Popup 等独立窗口拥有各自的输入、焦点记忆和待执行动作；只有当前有效窗口消费事件。焦点丢失、内容替换、窗口销毁或 detach 时撤销旧任务与监听。关闭弹层后恢复宿主的有效焦点，避免穿透操作背后页面。
3. **区分触摸模式与键盘焦点。** 镜腿原始触摸可能使系统进入 touch mode 并清除高亮；发方向/确认前恢复当前窗口的有效焦点。必要时采用对应框架的退出触摸模式/请求焦点机制，例如 View 的 `requestFocusFromTouch()`，而不是把所有控件永久设为 touch-mode focusable。
4. **区分 View 焦点与列表选中行。** ListView 可以仍有焦点但选中位置已变为无效；只检查 `findFocus()` 会导致确认无反应。优先读取当前窗口和控件的实时选中状态，记忆的列表、adapter、位置及 stable ID/条目身份仅作校验后的恢复线索；数据或 adapter 变化后重新定位，不能按旧位置点击新条目。RecyclerView/Leanback 同样要考虑复用和数据替换，但不要照搬 ListView 的 API。首次进入、原条目删除或内容整体替换时，按下文的恢复顺序建立新导航目标；无有效条目则不确认，旧目标的延迟确认不得转移过来。
5. **补齐本地按键分发缺失的焦点搜索。** 直接调用窗口 callback 的 `dispatchKeyEvent` 不一定经过 ViewRoot 的未处理方向键遍历。先让原逻辑处理；只有方向键未处理且焦点未移动时，才在当前窗口内做 `focusSearch/requestFocus` 或框架等价回退，避免移动两次。候选可能是自身不可聚焦、但含可聚焦子项的容器；检查归属、可见、启用及 `hasFocusable()`，让容器 `requestFocus(direction)` 执行原有子焦点和侧栏切换逻辑，不能仅凭 `isFocusable()` 把它排除。
6. **列表布局稳定后再确认。** 恢复 selection 后若仍待 layout/pre-draw，需要有界延迟，绑定原窗口、内容、焦点、adapter 和目标条目。布局等待期间目标变化、失焦、detach 或超时就取消，不能把积压的 CENTER 发给新页面。双击判定前延迟的单击也绑定原目标；第二击识别为返回时撤销第一击确认，避免先打开再退出。
7. **方向移动要保留业务导航。** 验证卡片网格跨行、滚动列表、侧栏分类与右侧内容之间的转移，以及弹窗按钮、单选列表和登录页动作。到边界不移动可能是正常行为；仅看到 DPAD 日志不能证明选中框移动。焦点变化时两眼高亮要同步刷新。
8. **操作后检测结果并自恢复。** 以当前窗口的实时焦点、逻辑选中项和布局/滚动状态判断导航结果；失效时重新扫描当前内容，按下文恢复。仅在下一次操作前恢复旧 View，或把按键返回 true 当作移动成功，都不满足此要求。

这些机制以当前框架和实际事件证据为准。SmartTube 的侧栏曾返回不可聚焦但含子焦点的容器；BBLL 的独立列表弹窗曾发生“View 有焦点、选中行已清空”。它们说明需要验证的边界，不要求所有应用复制同一实现。

## 光标恢复闭环：检测结果，再查找当前选中项

这是适配应达到的行为要求，不表示现有项目已经全部实现。恢复器集中放在窗口/导航适配层，为不同控件提供读取当前导航目标的接口，不在每个业务页面堆叠补丁。

**观察操作结果。** 方向操作前记录窗口和内容代次、当前焦点、逻辑条目身份/位置、有效导航区域及必要的滚动状态；操作后在正常分发完成或下一次 layout/pre-draw 时复查。View 引用相同不代表条目未移动，列表复用可能保持同一 View；引用改变也不代表导航成功，可能只是内容重建。`dispatchKeyEvent` 的 handled 值仅作为线索。

| 观察到的状态 | 处理 |
|---|---|
| 焦点/逻辑选中项有效移动，或发生符合该方向语义的滚动/区域切换 | 更新当前状态；无需额外移动 |
| 布局、滚动或内容加载尚未完成 | 等对应事件后复查，限制等待时长和回调数量；不每帧发方向键 |
| 当前选中项仍有效，沿该方向确实没有可达目标且无待完成转移 | 正常边界，保留当前项；不要重置到第一项 |
| 焦点为空、脱离当前树、选中行无效、候选隐藏/禁用，或出现失效的焦点关系 | 进入当前窗口的重新定位与恢复 |
| 焦点有效但有可达候选且没有移动，原因未明 | 检查当前导航区域、焦点搜索和原分发是否截获；仅在确认未消费时做一次有界回退，不强行跳过业务拦截 |
| 窗口/内容代次变化，或另一弹层成为当前窗口 | 取消旧操作观察、重试与确认；新窗口按自己的状态建立导航，不把旧滑动转发过去 |

**从当前内容重新定位，顺序如下：**

1. 读取当前有效窗口中仍可用的真实焦点及控件的当前导航选中项，例如列表 selection、Leanback 当前项或应用明确维护的活动项；先恢复“界面现在选中的那一项”。
2. 若当前没有有效导航项，在同一内容/数据身份下用稳定条目 ID 等线索寻找重建后的对应项；重新解析成当前 View，不只检查旧 View 是否还存在。adapter 或内容整体改变时旧索引不能直接复用。
3. 对当前树中的应用选中态进行候选发现时，核对活动区域和框架语义。`isSelected()`/`isChecked()` 可能只是已订阅分类、单选值或多选状态，不等同键盘焦点；不能取第一个高亮节点就当成当前导航项。优先使用组件 API/应用导航状态，歧义时采用应用默认焦点。
4. 原选中项确已消失时，先沿用当前页面/区域的默认焦点策略；否则选择该区域内首个可见且可操作项，必要时再选择其中首个可操作项。保留弱引用的祖先区域线索：整块列表被替换但外层内容面板仍在时，优先留在该面板，避免跳回全窗口的侧栏首项。嵌套网格还须校验祖先行的当前 selection；外层已选中其他行时，以新的选中路径定位，不能回到仍挂载的旧内层网格。若当前区域及其适用祖先均已消失，再重新确定当前页面的活动区域。
5. 恢复实际焦点及必要的 selection，处理 touch mode，并在布局稳定后再次验证窗口归属、条目身份、可操作性和双眼高亮。空列表/加载中没有候选时保持无确认状态，等数据/布局事件再尝试，不能无限轮询或吞掉返回操作。

**恢复与重试分离。** 恢复只建立导航目标，不执行点击/CENTER。原目标失效的延迟确认直接取消。方向操作仅在同一窗口/内容代次、已证明未移动且未被业务消费时，允许最多一次恢复后的方向重试；状态不确定、已发生滚动/转移或界面改变时只恢复，等待下一次用户输入。避免“一次滑动移动两项”、重试循环和跨窗口误操作。

**触发与验收。** 除方向操作后的检测外，在内容替换、adapter 更新、弹窗切换/关闭和窗口重新获得焦点后做合并的有效性检查；不要在每次绘制时强抢焦点。测试至少覆盖：原选中控件被重建、条目删除/排序、adapter 更换、列表有焦点但无选中行、异步加载后获得候选、弹窗替换时旧任务取消、正常边界不跳转、handled=true 但选中项未变、一次操作无重复移动，以及恢复后下一次方向和确认可用。

## 鼠标模式：小白点与单次点击

- 在单眼逻辑坐标中维护一个指针位置，用镜腿滑动增量更新并限制在有效内容区域；双眼呈现同一逻辑位置的小白点。不要让指针跨越整块双眼物理画布后只出现在一只眼里。
- 单击对当前窗口中的指针位置派发一组一致的按下/抬起事件或既有鼠标点击；坐标只转换一次，命中实际控件。指针绘制层不抢焦点、不拦截自己的点击，不向两眼各点击一次。
- 双击撤销待执行的单击，再按当前层返回；滑动、长按和取消不误点击。窗口切换/销毁时清除旧点击目标，检查新窗口的坐标与尺寸；普通鼠标、手柄输入继续保持可用。
- 鼠标平滑度、点击命中与自由位置移动单独验收，不能用光标模式 DPAD 成功替代。不得擅自把明确要求的小白点改成焦点导航。

## 两种模式的验收要点

光标模式至少核对四方向选中框移动、网格/列表滚动、侧栏向右进入内容、弹窗列表选择与确认、关闭后焦点恢复、异步页面、快速单/双击，以及操作中数据刷新/adapter 替换。鼠标模式至少核对两眼小白点位置、四方向自由移动、边界、按钮命中、弹窗内点击和双击返回。两者都验证单次动作不重复执行。

源码/补丁检查和自动化测试可验证分发、所有权和布局状态；ADB 注入不等于镜腿实测。用户暂停设备操作时保留物理方向、真实焦点移动、指针命中和双眼效果待验，不自行启动应用来补验。

## 先定位事件真正经过哪里

追踪链路：物理设备 → 系统/Mercury/SDK → Activity 的 touch、generic motion 或 key → 手势识别 → 页面动作。只读 probe 能列出设备名称与来源摘要，不能证明某次物理动作已到应用。

在目标页面短时记录 `deviceId`、设备名、`source`、`actionMasked`、`eventTime`/`downTime`、坐标及最终动作。记录动作所需字段即可；无需长期抓取全部用户输入。分别操作左右镜腿，确认系统是否也同时生成媒体键或 BACK。

- `cyttsp`、`capsense` 是已见过的设备名线索，后续型号要重新核实。
- “第一次遇到的 deviceId 是右镜腿”仅是现有代码的启发式；枚举顺序、重连和重启都可能变化。用实测身份/能力或可校准映射。
- `com.rayneo.mercury.app=true` 是本地项目的启动器标记。它和右眼区域 View 对原始事件转发的作用有代码注释与旧文档的不同说法，应按当前固件实测。
- 不要看到应用收不到事件就认定所有固件都会拦截。先确认当前前台窗口、事件 source、输入入口和系统处理。

## 系统左右反向：先确认坐标是否已经转换

用户要求跟随系统“自然移动方向”或“左右反向”时，先查设置写入点、系统读取者及应用实际收到的事件。找到一个 0/1 开关不代表应用需要读取它并再乘一次反号。系统已反转交付坐标时，保留坐标增量的符号就能跟随；重复反转会抵消系统设置。

已核实的定位线索：X3 Pro `ARGF20 / MercuryLiteXR`、Android 12/API 32、构建 `2BAU`，2026-09-11 的 BBLL 验证：

- Launcher 的 `SlideSwitchView` 将“自然移动方向”写入 `debug.rayneo.tp.rotation`；开关选中为 `0`，未选中为 `1`。这是系统属性，不是已确认的 `Settings.System/Global` 项。
- 从当前设备提取的 `libinputreader.so` 中，`TouchInputMapper::cookPointerData()` 调用 `rotateAndScale(float&, float&)`。当前显示方向为 0 时，该函数读取上述属性，值 `0` 使用正向 X 缩放，值 `1` 使用反向 X 缩放；Y 计算不变。转换发生在应用接收 MotionEvent 之前。
- 两次从耳后向镜片的物理滑动，在 `0` 下应用 X 增加、输出 `DPAD_RIGHT (22)`，在 `1` 下 X 减少、输出 `DPAD_LEFT (21)`。这验证了导航输入的系统联动；第二次位于左侧边界，发出 LEFT 不等于选中项必然继续左移。
- 鼠标和光标导航共用这些坐标且均保留 X 增量符号，因而有机制与代码依据判断两者都会跟随；该轮只做了导航模式的物理对照，不把鼠标模式写成已单独物理验收。

证据索引保留在 BBLL 本地 `_local/system-slide/device-20260911/`：`verification.json`、`physical-phase-0.log`、`physical-phase-1.log`、`rotateAndScale.disasm.txt`。所检系统库 SHA-256 为 `96d2c084de1eb6e71c85412686735b7bcbb9cea8ec480e766407d578f1868493`。这些用于复核历史依据，不是执行技能的依赖；原始设备日志不随技能发布。

换固件、显示方向、事件通道或应用时重新核对上述链路，不照搬属性值含义、反编译地址或触摸坐标范围。若应用收到的是 SDK 手势枚举、原始轴值或已经具有方向语义的按键，单独确认该层是否完成转换。外接蓝牙鼠标、手柄和普通 DPAD 不应仅因镜腿模式而进入额外反向分支。

对照测试应先启动短时、按标签过滤的日志捕获，再提示用户做同方向动作；记录阶段、设备来源、坐标增量、最终按键/鼠标位移及窗口归属。及时保存，避免小缓冲区或事后 `logcat -t` 截断 DOWN 等关键事件。ADB 的 `input swipe/keyevent` 在另一层注入，不能替代物理触控板经过 InputReader 的方向验证；底层 `sendevent` 即使文件权限看似允许也可能被系统策略拒绝。一次拒绝足以说明该回放路径未通过，不把应用层模拟成功改写成真实镜腿成功。shell 能读写属性也不证明普通应用 UID 具有同样能力。

## 临时切换方向开关与恢复

测试前同时记录当前运行值、持久化值及它们的优先级，预先安排恢复步骤。已在当前会话获准的可逆切换直接代劳并读回；写入成功只证明设置改变，输入效果另用事件证据验证。

上述 `2BAU` 系统库还在触摸处理时比较 `debug.rayneo.tp.rotation` 与 `persist.rayneo.tp.rotation`，不同则尝试把运行值同步到持久化值。现场 shell 可写 debug 属性，但直接写 persist 属性被拒绝。因此把 debug 恢复后，persist 仍可能保留测试值，要等下一次真实触摸触发同步。同步时机有系统库代码依据，实际恢复是否成功必须再读回，不能把预期同步写成已完成。

- 在开始测试时安排“原值下滑动 → 切换后同向滑动 → 恢复运行值 → 必要的真实触摸 → 核对两个值”，提前说明哪些动作用于验证、哪些用于恢复。
- 若初始两个值不同，先查明原因和恢复目标；不要默认都应设为 `0`。为测试开启的日志、应用常亮等临时状态也单独恢复，保留用户主动调整的其他设置。
- 证据足够时明确告知验证已完成。若用户停止配合，报告运行值、持久化值及具体待恢复项；不要把“下次正常触摸会同步”写成“所有设置已恢复”，也不要为完成清理自行重启设备或绕过权限限制。

## 右眼透明 overlay 的条件

本地实现将透明 View 放在右眼区域，接收 touch/generic motion 并将双击映射到返回。这是该应用的一条适配路径，加入 overlay 本身不证明手势转发正确。

需要它时：从实际眼区尺寸定位，安装一次；确认命中的事件属于期望设备/来源；验证不会截获鼠标、其他指针或 UI 点击。应用已经有镜腿识别或 SDK 通道时，先确定消费边界，避免 overlay、Activity 与系统同时触发一个动作。保持手柄和系统导航可用。

## 识别与业务动作分离

用单调时间或事件时间识别手势，处理 `ACTION_CANCEL`、移动超阈值、长按、pointer 数量及重复 release。若一次动作同时出现 `ACTION_UP` 与 `ACTION_BUTTON_RELEASE`，或同时进入 touch/generic 路径，依据实际事件流去重；单纯加大双击时间窗口不会修复重复动作。

应用动作通过一个入口分发，按当前状态决定行为：

| 页面状态 | 返回动作的典型语义 | 必须核实 |
|---|---|---|
| 弹窗、权限说明或菜单打开 | 先关闭当前层/取消 | 是否有导航 callback 或扫描正在提交 |
| 阅读/视频/游戏页面 | 返回或打开应用已有菜单 | 用户期待的是退出内容、暂停还是菜单；保留原业务语义 |
| 根页面 | 按产品约定返回系统或保留首页 | 不把全局双击直接等同 `finish()` |
| 系统拥有音量/媒体语义 | 未处理事件继续向系统传递 | 避免应用和系统同时加倍执行 |

接入项目现有导航/`OnBackPressedDispatcher`，检查 dispatcher 最终落到哪个 callback；调用 dispatcher 仍可能结束根 Activity。静态看见 `onBackPressed()`、虚拟 BACK 或 overlay 注释，都不构成行为验证。

输入 gating 保留页面与会话条件，例如 seek 仅对支持 seek 的本地播放开放，投屏/直播可禁用。游戏优先复用原手柄映射、焦点与菜单行为；不要为镜腿添加第二套游戏按键状态机。

验收按实际页面逐个操作：同一双击只触发一次，菜单关闭优先级正确，滑动/长按不误触，左右镜腿、系统返回与手柄均可用。静态 probe 不替代这一轮物理操作。
